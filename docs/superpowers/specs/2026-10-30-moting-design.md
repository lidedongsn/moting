# Moting 设计文档（MVP）

> 日期：2026-10-30
> 状态：已确认（2026-10-30，用户回复"自己用，干吧"）
> 说明：标注 **【我的决定】** 的条目是设计者代为做出的选择，用户未明确表态，可以推翻；其余为用户明确决定。

## 1. 这是什么、为什么做

Moting 是一个纯 macOS 原生的会议记录工具，面向视频会议（腾讯会议、钉钉、Zoom 等）场景，对标钉钉 / 腾讯会议自带的"会议纪要"能力，但不依赖任何会议平台：

- 会中：一个置顶的小悬浮窗，实时显示字幕，让人随时知道"刚才说了什么"。
- 会后：对完整录音做一次**高准确率**的离线重识别，然后调用大模型 API 生成概要、主要内容和待办，导出 Markdown。

用户最看重的两件事：**识别准确**、**性能好（在 M2 MacBook Air 16GB 上流畅，不拖慢会议软件）**。同时要求架构有拓展性，后续能换引擎、加功能而不推倒重来。

## 2. 目标 / 非目标 / 反目标

### 目标（MVP 必须做到）

1. 同时录制**麦克风**（我）和**系统音频**（对方），两路分开保存，原始录音永久保留。
2. 会中悬浮窗（字幕卡片样式）实时显示识别文字，区分"我 / 对方"。
3. 会后自动对完整录音做高准确率重识别（支持热词），并对"对方"一路做多说话人分离，结果替换实时草稿。
4. 会后调用用户配置的 OpenAI 兼容 API 生成：概要、主要内容、待办。
5. 主窗口查看历史会议、转写稿和 AI 结果，一键导出 Markdown。
6. 会中零干扰：不抢占、不修改音频设备，不压低其他 app 音量，不抢焦点。

### 非目标（MVP 不做，但架构要留位置）

- 自动检测会议开始 / 日历联动
- 全文搜索
- 点击字幕跳转回放 / 内置播放器
- 导入外部音频文件
- 用户自定义总结模板（内置一套即可）
- 本地大模型总结（Ollama、MLX 等，接口层兼容但不专门做）
- 云同步、多设备
- 导出到飞书 / Notion / 微信等第三方
- 线下会议（多人共用一个麦克风）的说话人分离：麦克风一路默认全部视为"我"
- 转写稿文字编辑（只支持说话人改名，见 5.6）

### 反目标（做出来也算失败的情况）

- 开会时让会议软件卡顿、声音变小、回声异常，或导致麦克风 / 耳机被切换。
- 用户共享屏幕时，悬浮窗内容被会议另一方看到。
- 录了一小时，因为崩溃或断电丢失录音。
- 录音离开本机（只有转写**文字**会发给用户自己配置的 API）。
- 会后识别结果不如实时草稿准确（重识别的意义就是更准）。

| 语言 | 中文为主，需要处理中英混说 |
| 识别 | 实时和会后识别都必须**完全在本机**完成 |

```
[菜单栏图标 / 主窗口] 点"开始录音"
        │
        ▼
悬浮窗出现（字幕卡片），实时字幕滚动
  ├─ ★ 标记重点（记下时间点）
  ├─ ⏸ 暂停 / 继续
  └─ ■ 结束
        │
        ▼

        │
        ▼

        │
        ▼
系统通知"会议纪要已生成" → 点开进入主窗口该会议详情 → 导出 Markdown
```

## 5. 功能说明

### 5.1 录音

- **麦克风**：通过 Core Audio / AVAudioEngine 读取当前选定的输入设备。默认跟随系统默认输入，设置里可手动指定。
- **系统音频**：Core Audio Process Tap（`CATapDescription`）。
  - `muteBehavior` 必须为不静音，保证用户照常听到对方。
  - 采集范围：MVP 采用**全局系统音频、排除本 app 自身**【我的决定】。只录会议软件进程更干净，但腾讯会议等可能从子进程发声，可靠性需实测（见第 8 节）。若实测可行，可以加"只录指定 app"选项。
- **零干扰原则（硬性要求）**：
  - 不得开启系统 voice processing（`setVoiceProcessingEnabled`），它会压低其他 app 的音量。
  - 不得修改设备的采样率、缓冲区大小等参数；按设备原生格式读取，在 app 内部重采样。
  - 不在非录音状态打开麦克风（会把蓝牙耳机切到通话模式）。
  - 不使用 hog mode。
- **设备切换**：录音中插拔耳机、切换默认设备时，自动接到新设备继续录，不中断，并在时间线上保持连续。
- **崩溃安全**：两路音频边录边落盘（增量写入，可恢复的格式）。app 崩溃或断电后，重启时能找回已录部分，并把该会议标记为"录音中断"，仍可继续走会后流程。
- **暂停**：暂停期间不写入音频；时间线记录暂停区间。
- **标记重点**：记录时间戳（相对会议开始），存入数据库。

### 5.2 悬浮窗（字幕卡片，用户选定 B 款）

- 基于 `NSPanel`：`nonactivatingPanel`（不抢焦点）、浮动层级置顶、`canJoinAllSpaces` + `fullScreenAuxiliary`（能浮在全屏会议软件之上）、可拖动整个窗口。
- 布局：
  - **顶部**：拖动区、录音红点、计时、音量电平、收起按钮
  - **中间**：滚动显示最近 4–6 句字幕。"我"和"对方"用不同颜色区分；未定稿的片段（流式识别中间结果）显示为灰色，定稿后变为正常颜色
  - **底部**：★ 标记重点、⏸ 暂停、■ 结束
- 宽度约 290pt，可以调整大小；可调透明度；记住上次的位置、大小和透明度【我的决定】。
- **收起态**：缩成胶囊条，只显示红点、计时和最新一句【我的决定】。
- **共享屏幕时不可见**（硬性要求）：首选 `NSWindow.sharingType = .none`。新版 macOS 的部分采集方式可能无视该设置，需要实测。不可靠时，退而检测到正在共享屏幕就自动隐藏悬浮窗。实测结论要写进代码注释和文档。
- 会议结束后悬浮窗显示会后处理进度，可手动关闭。

### 5.3 实时识别（会中，草稿质量）

- 引擎：sherpa-onnx 流式模型（中英双语流式 Zipformer 或流式 Paraformer，由基准测试决定）。
- 两路分别识别：麦克风一路标为"我"，系统音频一路标为"对方"。
- **实时回声消除**：用户外放时，麦克风会录进对方的声音。在 **app 进程内**对麦克风数据做回声消除，以系统音频一路作为参考信号（如 WebRTC AEC3 或 SpeexDSP，由实现者选）。这只处理 app 自己拿到的那份数据，不影响任何其他 app。
- 性能目标（M2 Air，录音 + 实时识别同时运行）【我的决定，需在实现中验证】：
  - 平均 CPU 占用 ≤ 单核 30%
  - 常驻内存 ≤ 600MB
  - 字幕延迟 ≤ 1.5 秒
- 实时识别结果存为该会议的"草稿"版本转写。

### 5.4 会后处理（准确率优先）

由一个**持久化的后台任务队列**驱动，每个步骤是独立、可重跑、可断点续跑的任务：

1. **回声处理**：用系统音频一路作参考，对完整的麦克风录音做离线回声消除 / 去重，避免外放时同一句话出现在两路。
2. **精准重识别**：对两路音频做非流式识别。
   - 先用 VAD 切段，再识别，并补全标点。
   - 支持热词（人名、产品名、术语），对准确率提升最明显。
   - 引擎候选：Paraformer-large、SenseVoice、Whisper large-v3 / turbo（WhisperKit）。默认引擎由基准测试决定（见第 8 节），要求是中文与中英混说的综合准确率最高，同时支持热词或提示词。
3. **说话人分离**：对"对方"一路做离线说话人分离（sherpa-onnx 或 FluidAudio），得到"说话人 1、2、3…"。麦克风一路固定为"我"。
4. **合并对齐**：两路片段按时间合并成一份带说话人的完整转写稿，作为"正式稿"版本保存；草稿保留不删。
5. **AI 处理**：见 5.5。

调度规则：

- 任务严格串行，同一时间只加载一个大模型，用完即释放，控制内存峰值。
- 显示整体进度和当前步骤。
- **电源策略**【我的决定】：插电时会后立即开始；使用电池时，在悬浮窗或通知里提示"插电后自动处理 / 现在处理"，默认插电后再处理。
- app 退出或崩溃后重启，未完成的任务从最近完成的步骤继续。
- 用户可以对任何会议手动"重新转写"或"重新总结"（比如换了引擎、改了热词或换了 API），每次生成新版本，不覆盖旧版本。

性能目标【我的决定，需在实现中验证】：M2 Air 插电时，1 小时会议的会后处理（不含 AI 总结的网络时间）在 15 分钟内完成。

**准确率与速度冲突时，准确率优先**（用户原话："离线再识别一次，确保准确性"）。【我的决定】基准测试中最准的引擎只要 1 小时会议的处理时间不超过 60 分钟、内存峰值不超过 8GB，就作为默认引擎，15 分钟目标相应放宽；超出这个范围则选次优引擎。MVP 不做"快速 / 精准"两档切换，但引擎可以在设置里手动选。

### 5.5 AI 总结

- **服务配置**：OpenAI 兼容的 Chat Completions 接口。设置项包括：
  - 名称
  - Base URL
  - API Key：存入钥匙串，不得明文落盘
  - 模型名

  可以保存多套配置并选一个默认【我的决定】，内置 DeepSeek 的预设（Base URL 和模型名预填）【我的决定】。
- **隐私提示**：首次配置时明确告知"转写文字会发送到你配置的服务，录音不会上传"。
- **输出内容**：
  - **概要**：一段话
  - **主要内容**：按议题分条
  - **待办**：每条包括事项、负责人（如能识别）、截止时间（如提及）
  - **决策**：会上明确拍板的事项【我的决定，额外增加的小项】
- **输出格式**：要求模型返回结构化 JSON（如服务支持 JSON 模式就开启），由 app 校验后渲染。解析失败时重试一次，仍失败则保存原文并提示。
- **★ 标记**：把标记的时间点和附近原文一起提供给模型，要求在总结中优先体现【我的决定】。
- **长会议**：转写稿 token 数超过所选模型的上下文上限（留出安全余量）时，先按时间或议题分段总结，再汇总。上下文上限在服务配置中可填，有默认值。
- **错字纠正**：MVP 不做自动纠正，以免改动原文。热词已经能解决大部分专有名词问题【我的决定】。
- Prompt 模板做成独立资源文件，代码中不硬编码，为以后开放自定义模板做准备。

### 5.6 主窗口

【我的决定，用户未讨论细节】

- 左栏：会议列表，按时间倒序。显示标题（默认"会议 + 日期时间"，可改名）、时长、处理状态（录音中 / 待处理 / 处理中 / 完成 / 失败）。
- 右栏：会议详情，分两个标签页。
  - **纪要**：概要、主要内容、待办、决策。
  - **转写稿**：带说话人和时间戳的全文；★ 标记处高亮；可以切换查看草稿版 / 正式版。
- 说话人改名：把"说话人 2"改成真实姓名，转写稿、纪要和导出同步更新。
- 操作：导出 Markdown、重新转写、重新总结、删除会议（同时删除录音）。
- 菜单栏常驻图标：开始 / 结束录音、打开主窗口、显示会后处理状态。

### 5.8 设置

- **音频**：输入设备（默认跟随系统）、系统音频采集范围。
- **识别**：模型管理（下载 / 删除 / 选择实时引擎和会后引擎）、热词表（全局一份，每行一个词）【我的决定：MVP 只做全局热词】。
- **AI 服务**：多套 API 配置、默认选择、测试连接。
- **会后处理**：电源策略。
- **存储**：数据目录位置、当前占用空间。

### 5.9 模型分发

- 模型不打包进 app，首次使用时引导下载。默认来源为 ModelScope，可切换到 HuggingFace【我的决定】。
- 支持断点续传、SHA 校验，下载失败可重试。
- 模型清单（名称、版本、文件、大小、校验值、用途）由 app 内置的 manifest 描述，为以后在线更新清单留出空间。

## 6. 架构

### 6.1 模块划分（Swift Package，多 target）

```
MotingApp (SwiftUI/AppKit，app 层：主窗口、悬浮窗、菜单栏、设置)
   │
   ├── Core        领域模型、协议定义、事件总线、时间线
   ├── Capture     AudioSource 实现：MicSource、SystemAudioTapSource；重采样；增量落盘
   ├── DSP         回声消除（实时 + 离线）、VAD
   ├── ASR         ASREngine 实现：sherpa-onnx 流式 / 离线、（候选）WhisperKit
   ├── Diarization Diarizer 实现：ChannelDiarizer（按声道）、Speaker 分离实现
   ├── LLM         LLMProvider：OpenAICompatibleProvider；Prompt 模板；结构化输出解析
   ├── Pipeline    持久化任务队列、会后处理各步骤（Job）
   ├── Storage     SQLite（GRDB）、文件布局、迁移
   └── Models      模型 manifest、下载、校验
```

另有一个命令行工具 target `moting-bench`：对一组带标注的音频批量跑各 ASR 引擎，输出字错率（CER）、速度和内存。用于第 8 节的引擎选型，以后换引擎时也用它回归测试。

### 6.2 关键接口

接口为示意，具体签名由实现者定，但要满足以下能力：

```swift
protocol AudioSource {          // 输出：带时间戳的 PCM 块 + 设备变化事件
    func start() async throws
    func stop() async
}

protocol StreamingASREngine {   // 会中：喂音频块，吐出 partial / final 片段
}

protocol OfflineASREngine {     // 会后：整段音频 + 热词 → 带时间戳的片段（含标点）
}

protocol Diarizer {             // 音频 → [(start, end, speakerLabel)]
}

protocol LLMProvider {          // messages → 文本 / JSON；支持取消；可报告上下文上限
}

protocol PipelineJob {          // 可持久化、可重跑、幂等；有输入 / 输出版本号
}
```

拓展点和接口的对应关系：

| 将来要做的事 | 做法 |
|---|---|
| 导入音频文件 | 新增一个 `AudioSource` |
| 换识别引擎 / 接 SpeechAnalyzer | 新增一个 `ASREngine` 实现 |
| 本地 LLM | 走 `OpenAICompatibleProvider` 接 Ollama，或新增一个 `LLMProvider` 实现 |
| 自定义模板 | 开放模板资源 |
| 全文搜索 | 在 Storage 加 FTS5 |

### 6.3 数据存储

- 数据目录：`~/Library/Application Support/Moting/`
  - `moting.sqlite`
  - `meetings/<meeting-id>/mic.*`、`system.*`：两路原始音频
  - `models/`：下载的模型
- 音频格式由实现者决定，要求：边录边写、崩溃后可恢复、无损或接近无损（保证会后识别质量）。录音结束后可以转成更省空间的无损格式归档（如 FLAC / ALAC）。
- 数据库主要实体：
  - `Meeting`：标题、开始 / 结束时间、状态、暂停区间
  - `AudioTrack`：会议、声道类型（mic / system）、文件路径、格式
  - `TranscriptVersion`：会议、类型（draft / final）、引擎、模型版本、热词快照、创建时间
  - `Segment`：版本、开始、结束、声道、说话人 ID、文字
  - `Speaker`：会议、标签（说话人 1）、显示名（张三）
  - `Mark`：会议、时间点
  - `Summary`：会议、所基于的转写版本、Provider 配置名、模型名、模板版本、结构化内容（JSON）、创建时间
  - `Job`：会议、类型、状态、进度、错误、重试次数

### 6.4 线程与性能原则

- 音频回调线程只做拷贝入环形缓冲区，不分配内存、不加锁、不做 I/O。
- 实时识别、AEC、落盘各在独立的串行队列或 actor 上运行。
- 会后任务在低优先级（utility / background QoS）运行，不影响前台。
- 模型按需加载，用完即释放。

## 8. 必须先验证的风险（第一阶段）

正式开发前，先用一次性的验证程序和 `moting-bench` 回答以下问题，结论写回本文档：

1. **会后引擎选型**：比较各候选引擎的 CER、热词效果、M2 Air 上的耗时和内存峰值。用户未提供标注录音，【我的决定】数据来源：
   - 公开中文测试集的子集（如 AISHELL-1 test）
   - 公开的中英混说测试集子集
   - 2–3 段自录的模拟会议，带术语，人工校对参考文本

   日后用户积累了真实会议录音，用 `moting-bench` 复测。
2. **实时引擎**：对比候选流式模型的延迟、CPU 和准确率。
3. **系统音频采集**：在腾讯会议、钉钉、Zoom 中验证全局 Tap 和单进程 Tap 能否稳定录到对方声音；验证录音期间对方声音音量不变。
4. **零干扰验证**：录音期间，会议软件的麦克风、回声消除、音量是否完全正常；AirPods 场景是否正常。
5. **共享屏幕隐藏**：在腾讯会议、钉钉、Zoom 共享屏幕时，`sharingType = .none` 是否生效；不生效则验证自动隐藏方案。
6. **外放回声**：外放场景下，实时 AEC 和会后处理能否消除重复。用户未说明戴耳机还是外放，【我的决定】两种都支持。先打通戴耳机的主路径；实时 AEC 在主路径可用后接入，但必须在 MVP 内完成。

推进方式【我的决定】：验证和开发并行。与引擎无关的部分（Capture、Storage、Pipeline、悬浮窗、主窗口、LLM）可以先开工；引擎默认值等基准结果出来后，把结论写回本文档并告知用户，不阻塞其他开发。
